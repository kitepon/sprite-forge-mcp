# LoRA更新と生成経路の監査（2026-09-07）

オーナーの「更新されていない／更新したLoRAで生成していないのでは」という疑いに対する独立検査。対象は直近のowner・collar・layoutの3条件。新しい学習と製品コード変更は行っていない。

## 実測

- GPU機の元LoRAと3出力をsafetensorsから直接読取り。各1428配列のうち560配列が更新され、学習記録の差分二乗和と一致。元ファイルのSHA-256も各学習記録に一致。
- 実画像のPNGに含まれる生成条件を全30組で照合。LoRA名以外は同一。ComfyUI側の成功履歴も30件取得。
- 実機のComfyUI・同じPython環境の読込み関数を独立CPUプロセスで実行。各3条件の更新対象280層すべてが対応し、合成後の重みも280層すべてで変化。bfloat16化後も全280層に数値差が残る。本文の検査は更新対象DiTに限定し、診断時のclip=Noneによる未読込み警告を製品の異常と数えない。
- 元LoRAとowner更新LoRAをバイトコピーした新しいファイル名で実ComfyUIサーバーへ投入。seed601の各画像が前回と画素単位で完全一致（MAE=0）。新しい名前によるディスク読込みでも過去の結果が再現した。

## 結論と限界

直近3条件の保存更新と生成への反映を確認。ownerは実サーバーの再読込み再現も確認。今回の無改善を「元LoRAの使い回し」で説明する証拠は見つからない。NG抑制の学習目標・条件付け・更新量の妥当性はこの検査で証明していない。過去の全試行への一括した正常宣言にも使わない。

前回の生成開始時にWindowsパスをUnixのPath.nameで処理した不具合があり、HTTP400で失敗した。その原因を前回修正した後の40枚が比較対象。今回の履歴照合はその成功分を対象とする。

診断操作ではMacのaiterm経由のHTTP接続がNo route to hostで失敗し、要求送信前の失敗を確認したうえで通常のmain-server経路から実行した。また結果回収時のscpがディレクトリを一段深く作ったため、ファイルを明示して正しい位置へコピーして表示処理を再実行した。いずれもモデル・学習結果の障害と数えない。
