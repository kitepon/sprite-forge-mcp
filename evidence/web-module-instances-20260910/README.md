# WebUI のモジュール二重読み込みを外した実測（2026-09-10）

対象は本番 `http://192.168.1.2:8766`。commit `21606d4`（`?v=` 除去）、`16f9248`（CI 検査）、`7a714e8`（未選択時の第1工程の修理）を反映した状態で採取した。

Playwright は隣接プロジェクト `blog-figmaker` の依存を `createRequire` で借用しており、このリポジトリへは追加していない。

## 何を確かめたか

`web/main.js` などが `./jobs.js` と `./jobs.js?v=studio-4` の両方を import していたため、ブラウザーは同じファイルを別モジュールとして 2 回評価していた。購読側と発火側が別インスタンスに分かれるので、制作状況の更新が届かない。版番号を全部外した後、実ブラウザーで「同じファイルが 1 回しか読まれないこと」を数えた。

## 結果

- **モジュール要求は全ファイル 1 回ずつ。** `style.css` と JS 13 本（`main.js` `api.js` `ui.js` `flows.js` `jobs.js` `drafts.js` `layout.js` `state.js` `intent.js` `learning.js` `strength.js` `preview.js` `training.js`）が、18 画面を通した 1 セッション中に各 1 要求。`queryStringRefs` は空。
- **版番号付きだと本当に別インスタンスになる。** 同じページで `./jobs.js` と `./jobs.js?v=studio-4` を動的 import し、前者の購読者へ 7 秒間に届いた `emit()` を数えた対照実験で、素のパスは 3 件、版番号付きは 0 件、`sameInstance: false`。修理前の配線が実際に進捗更新を落としていた証拠。
- **`/api/jobs` は 10 回。** 巡回中の実測値で、購読が一本化された後も過剰な取得は起きていない。
- **横あふれなし。** 18 画面すべてで `scrollWidth === innerWidth`（デスクトップ 1280、スマホ 390）。制作状況の画面だけ `span` 3 個が視野の右端をわずかに越えて報告されるが、文書のスクロール幅は広がっていない。
- **コンソール異常なし。** デスクトップ・スマホともエラー 0 件。

## 巡回中に見つけた欠陥と修理

第1工程のスクリーンショットに「読み込めませんでした / Cannot read properties of null (reading 'approved_sheet')」が写っていた。原因は `web/flows.js` の `refreshContext` で、キャラクター未選択時に `null` になる `rec` を `rec.approved_sheet` と素で参照していたこと（`git blame` は `5ba00e67`、設定画を承認シートから作る改修と同じ commit）。直後の行と後続の分岐はどれも `null` を扱っており、この 1 行だけが漏れていた。

キャラクターを選ぶ前は誰でもこの画面に入るので、新しく使い始めた人には最初の画面が必ず壊れて見える。`rec?.approved_sheet || rec?.bible` に直し、`tests/web-flow.test.mjs` へ `flow()` を実際に起動する回帰試験を足した（この試験ファイルはそれまで `flow()` を呼んでいなかったので、欠陥を捕まえる術がなかった）。修正を戻すと新しい試験が落ちることも確認した。

コンソール監視がこの欠陥を素通りしたのは、`errorState()` が例外を捕まえて DOM へ書くため。修理後の確認スクリプトは、コンソールではなく描画された「読み込めませんでした」の有無を見る。

## 修理後の本番確認

デスクトップ 1440×900・スマホ 390×844 の両方で、エラー表示なし、`approved_sheet` の文字なし、見出しは「キャラクターを育てる／キャラクター／これから始まる一枚」、未選択の案内文が出ており、横あふれ 0、コンソール異常 0（`sf-verify-sheet.json`）。
