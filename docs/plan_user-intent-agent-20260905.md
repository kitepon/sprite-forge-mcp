## エージェントと既存処理の分担

エージェントは、参考画像を読む、注文の対象と有効範囲を判断する、既存の条件との違いを整理する、生成用の指示を提案する役を担う。画像生成と学習の実行は、既存の共通サービスとComfyUI／sd-scriptsが担う。

最初は画像と台帳の読取り、および指示案の出力までに限定する。後で、ユーザーが確定した指示を既存サービスへ渡す工程をつなぐ。任意のコード・シェルを書いて本番へ適用するエージェントにはしない。

### 保存する内容の区別

| 内容 | 用途・有効範囲 |
| --- | --- |
| コメント原文 | ユーザーが何を頼んだか。解釈で置き換えず残す |
| 画像の観察結果 | その画像に実際に写っている衣装・形・構図。学習用の説明の根拠 |
| 共通の制作条件 | 本人の特徴、採用する衣装・画風など。ユーザーが継続を意図した条件 |
| 今回の注文 | 今回のポーズ・場所・表情など。共通条件へ自動昇格させない |
| パネルの修正 | 指定されたパネルだけ。既存のパネル修正の保存方針を維持 |
| 解釈と実行の記録 | 参照画像、適用範囲、変更前後、実際のプロンプト・否定条件・モデル設定・結果 |

「4枚目」は注文時点の表示順から、既存のキャラクターkey・sample index・pathに結び付ける。後で画像を削除したり順番が変わったりしても、現在の4番目へ付け替えない。既存のjob_idを生成結果との対応に使い、新しい全体ID体系は作らない。

「この絵の赤い服」は観察、「この絵も青い服にしたい」は希望である。赤い服の教材に青い服という説明を付ける実装にはしない。複数画像間の優先関係は、どの特徴について優先するかも持つ。衣装の注文から顔・髪・画風の変更を推測しない。

新しい注文は同じ対象・範囲の条件を更新し、無関係な条件を残す。「今回は」「今後も」などを解釈し、有効範囲が判断できなければその点だけ質問する。全コメントを連結してプロンプトに入れる方式は採らない。

### 生成モデルへの渡し方

Animaの公式資料は、タグ・自然文・その併用とプロンプトの重み付けを説明している。どの表現が今回のLoRAで有効かは実測する。日本語の単語置換表、衣装専用の定型語、固定の画風句は追加しない。[Anima公式モデルカード](https://huggingface.co/circlestone-labs/Anima)

「強く採用」をLoRA全体の強度増加へ機械的に変換しない。LoRAの強度は4枚目の衣装だけを指す値ではない。まず対象画像から読んだ特徴の明示、競合する指定の整理、Anima用の表現を比較する。プロンプトの強調を試す場合も実際のComfyUIグラフと画像で確かめる。

学習素材の選択や反復数の調整は別の実験にする。プロンプト変更と再学習を同時に行わず、何が改善に寄与したか分けて確認する。画像加工、教材の重み付け、再学習が必要になったら変更内容を提示し、実行の合意後に行う。

## 同条件での比較方法

### 解釈の試験セット

ベルの4枚を使う例に加え、別キャラクターまたは異なる衣装・小物の例を用意する。素材の使用範囲は実測前に確認する。調整に使わない例も残し、ベル向けのプロンプトに過適合していないか確かめる。

1. 「4枚目の画像の衣装を強く採用して欲しいなー」。4枚目の服を具体化し、衣装だけを優先する。
2. 同じ注文のまま画像の順序を変える。新しい4枚目を正しく読む。過去の注文は過去の画像を指し続ける。
3. 「顔は1枚目、服は4枚目、絵柄は変えない」。特徴ごとの参照先を混ぜない。
4. 「今回は横向きで、笑顔」。共通の衣装を維持し、横向きと笑顔は今回に限定する。
5. 「やっぱり今後は2枚目の服にして」。同じ範囲の旧指定を更新する。
6. 「この画像では赤い服だけど、作る絵は青にしたい」。教材の観察と制作の希望を分離する。
7. 「表情だけ変えて」。衣装・髪・画風の条件を保持する。
8. 「このパネルの帽子を外して」。対象パネルの修正と全体設定を分ける。
9. 「この絵のような筆のタッチにしたい」。画風の希望をキャラクターの衣装へ混ぜない。
10. 存在しない画像番号、参照画像の削除、対象の不明な「あれ」。対象を捏造せず、必要な確認事項を返す。
11. コメント中に引用や画像内文字がある。作品内の文字を制作指示と取り違えない。
12. 上記の考え方をベル以外の素材と新しい言い回しで試す。固有の衣装語に依存しない。

代表ケースの初回比較は既存の実測を使う。Sonnet除外の裁定に伴い、当初の上位2系統×12ケース×3回を、Terraの12ケース×3回（36応答）の品質検証へ変更する。参照先、適用範囲、未指定の特徴の維持、別素材への一般化を確かめる。新しい指示での2系統比較を完了したとは扱わず、候補除外と品質の合否は分けて記録する。残量を見て試行数を分割し、追加利用へ移行しない。

全候補へ同じ画像順・画像内容・ユーザー原文・既存条件・出力項目を渡す。モデルごとの画像縮小、画像詳細設定、推論設定、追加のツール読取りは記録する。意味の指示を特定候補だけ補って比較しない。失敗も残し、都合のよい応答だけ選ばない。

評価項目は、参照先の正しさ、見えている特徴の具体性、原文の希望の保持、適用範囲、矛盾の解消、未指定の変更の有無、出力形式、所要時間。総合点だけで決めず、誤った画像を指す・希望を落とす・別の特徴を勝手に変える失敗を個別に示す。これらは開発時の人による受入基準であり、製品に画像の自動合否判定を追加するものではない。

### 生成画像での比較

まず、既存LoRAとAnimaの版・強度・sampler・step・CFG・解像度を固定し、現行プロンプトとエージェントが組み立てたプロンプトを同じseed 1・2で比較する。最初のベル実験は2条件×2seedの4枚。再学習はしない。

確認するのは指定した衣装構造、顔・髪などの維持、画風の維持。ベルの場合は上下が独立した服か、腹部の露出が参照と合うかを確認する。これはその依頼の評価例であり、製品の固定条件にはしない。

改善が見えたら、別素材・別の指示を含む4ケース×3seed×新旧2条件の比較へ広げる。選んだ1枚だけで成功にしない。解釈は正しくても絵が変わらなければ、プロンプトへの変換、LoRAの影響、学習素材を順に切り分ける。教材や学習条件の比較は別の実験記録で行う。
